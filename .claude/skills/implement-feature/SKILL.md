# Implement one task of a feature

Target feature: **$ARGUMENTS**

You are the supervisor. You run in the main conversation, hand ONE task to the developer agent (`.claude/agents/developer.md`), check its work yourself, and commit only after the user says yes.

Rules: never edit specs, plans or the developer agent from this skill. The one exception is the single Decisions-log line in step 5, and only on the user's yes. Never switch models. Never push. One task per run.

## 1. Gate

- Resolve the ID. Accept `F1`, `f1` or `1`. No argument → list `docs/plans/` and ask which feature.
- Find `docs/plans/F<N>-*.md` and `docs/specs/features/F<N>-*.md`. If either is missing, stop and say so.
- Read the `_Status:` line of both. If either is not `Approved`, stop and name the file and its status. A plan needs `/plan-feature F<N>`; a spec needs `/spec-feature F<N>`.
- Run `git status --porcelain -- app/`. If anything is listed, stop and ask: "Uncommitted changes under app/: <list>. They may be left over from an earlier run. Keep them or discard them?" Do not continue until the user answers.

## 2. Pick the next task

- Read the plan's tasks in order. Each heading looks like `### F<N>.T<k> — <title>`.
- A task is **done** if `git log --format=%s` has a subject starting `F<N>.T<k>:`. Check the whole log.
- The **next task** is the first one that is not done. If none is left, say "F<N> complete" and stop.
- Read its `Depends on:` line. If any dependency is not done, stop and say which one.

## 3. Build the task message

- Show the user the task ID and title, then send the message.
- The message contains:
  - the task ID and title;
  - the task block copied word for word from the plan, from its `### ` heading up to the next `### ` or `## ` heading;
  - the AC IDs that the plan's "Acceptance criteria map" table assigns to this task (rows whose Task column lists this task, for example `T6`);
  - the paths to the spec (`docs/specs/features/F<N>-<slug>.md`) and the plan (`docs/plans/F<N>-<slug>.md`).
- Never include the rest of the plan.
- Call the developer agent with this message.

## 4. Check the work yourself

Do not trust the agent's report. Run each check and record the result.

- **Tests:** from `app/`, run `npm test`. Record pass and fail counts. If `app/` does not exist, the tests cannot run; say so.
- **Typecheck:** from `app/`, if `package.json` has a `typecheck` script, run `npm run typecheck`. If it has no such script, run `npx tsc --noEmit` yourself. Never rely on the agent's run.
- **Done when:** run every command named in the task's "Done when" yourself and record the result. If it needs a database, use a throwaway file (`DATABASE_URL=/tmp/<task>.db`), then delete it. If a check can't be run automatically, say "not run: <reason>".
- Never pipe a check command through `tail`, `head` or `grep`; exit codes must be visible.
- **Files:** compare `git status --porcelain` with the task's `Files:` list plus the test files it adds. Ignore everything under `docs/activities-outputs/` (the session-log hook writes it). Sort every other extra file into one of two lists:
  - **Generated by tools:** `app/package-lock.json`, `app/next-env.d.ts`, and files created by the Next.js scaffold (for example `app/src/app/layout.tsx` when the task is F1.T1). Anything in this list is safe to stage if the task's work created it.
  - **Unexpected:** every other extra file. Anything under `docs/specs/`, `docs/plans/` or `.claude/` is always unexpected, even if the agent says it changed it for a good reason.
- **ACs:** for each AC ID for this task, check that a test name in `app/tests/` or `app/src/` starts with that ID. List any AC with no such test.
- **Human approval:** if the task says `Needs human approval: yes`, or the agent lists items under "Needs human review", flag them clearly.

## 5. Show the result

In this order:
1. The agent's report, word for word.
2. Your checks: test pass and fail counts, the two file lists, ACs with no test, and human-review items.
3. **Decisions-log line (only if needed).** If the task's `Work:` asks to record something in a doc (for example "Record the Next.js version in the Decisions log"), the agent cannot edit docs, so it reports the value. Show that value to the user and ask: "Add this line to the Decisions log of docs/plans/F<N>-<slug>.md? (yes/no)". Only on a yes, add that one dated line to the plan's Decisions log and touch nothing else in the plan or spec. On a no, skip it. Either way, this is the only doc edit this skill ever makes.

If the agent's status is not `Done`, say so at the top.

## 6. Retries

- Retry only when the status is `Partial` or a check in step 4 failed. Send the developer agent the same task message plus the exact failures, copied from the output. Same model.
- If the status is `Blocked`, **do not retry**. Show the reason the agent gave, and ask the user to clarify the plan task. Then stop.
- Never run the agent more than 2 times per task.
- After 2 runs that still fail: stop, show what is still failing, and tell the user to clarify the plan task, then rerun `/implement-feature F<N>`.

## 7. Commit only on a yes

Before asking, list exactly what will be staged:
- the task's `Files:` list;
- its test files;
- any "generated by tools" extras from step 4;
- the Decisions-log line, if the user approved it in step 5;
- `app/.gitignore`, if it changed;
- `docs/activities-outputs/session-logs/` and `docs/activities-outputs/usage.md`.

Never stage an "unexpected" file unless the user names it. Never stage `node_modules/`, `.next/`, `.env` or `*.db`, even if the status shows them.

If the task's `Needs human approval` is `yes`, put this line above the question:
`⚠ Needs human approval: <reason from the task>. Review these files before answering.`

Then ask: `Commit F<N>.T<k>: <title>? (yes/no)`

- **No:** leave everything uncommitted and stop.
- **Yes:** `git add` exactly the list above, then `git commit -m "F<N>.T<k>: <title>"`. The subject is exactly that, with no trailers. Never run `git push`.

## 8. After the commit

Tell the user: "Run /clear before the next task."
