# F3 — People · Plan

_Status: Approved · Last updated: 2026-11-19 · Spec: [F3-people.md](../specs/features/F3-people.md) (Approved 2026-11-19)_

## Approach
F3 adds the person record, its four operations (list, add, find, remove) and the "in use" check that blocks removal. Pure rules go in `src/domain/`: the name check (trim, blank, 50 characters), the duplicate key (lowercased name), the oldest-first order, the dialog choice and the copy. None of these import the database, Next.js, iron-session or argon2. Each operation is a service in `src/services/` that receives the session, the `PersonStore` port, the `PersonUsage` port, `now`, `newId` and the logger. Every service calls `requireUser` (F1.T15) first, so the owner always comes from the session (F3.R11). The `PersonStore` takes the owner id and the trip id on every method, and the Drizzle store checks that the trip belongs to the owner before it reads or writes a person. This is the same pattern as F2's `TripStore`. The duplicate rule is enforced twice: the service reads the store's answer, and the database has a UNIQUE index on `(trip_id, name_key)`, so two simultaneous adds of "Sam" and "sam" cannot both be saved (F3.R4). The removal check is a separate `PersonUsage` port, so the rule (F3.R9) is unit-tested with a fake. The real check reads expense and payment tables that F4 and F6 create. Until then there are no expenses or payments, so the wiring reports every person as not in use, and F3.AC9 works when F3 is built (see Decisions log). The check stays behind the port. The route handlers in `src/app/api/trips/[id]/people/` only parse the request, call a service and map the result to a status code. The people section and the remove dialog are client components on the trip page built in F2.

**Build dependency:** F2 must be built first (F2.T1–T13, which in turn needs F1). F3 is build step 3 in product.md. F3 has no setup task of its own; the scaffold is F1.T1.

## Data model changes
One new table, `people` (migration generated by Drizzle; human approval required):

| Column | Type | Constraints |
|---|---|---|
| `id` | TEXT | PRIMARY KEY (UUID from `newId`) |
| `trip_id` | TEXT | NOT NULL, REFERENCES `trips(id)` ON DELETE CASCADE |
| `name` | TEXT | NOT NULL, CHECK (`length(name) BETWEEN 1 AND 50`); stored trimmed, capitals kept |
| `name_key` | TEXT | NOT NULL; the trimmed name in lower case, set by `personNameKey` in domain code |
| `position` | INTEGER | NOT NULL; 1, 2, 3… per trip in the order added (F3.R6) |
| `added_at` | TEXT | NOT NULL (ISO 8601, UTC) |

Constraints and indexes:
- `UNIQUE (trip_id, name_key)`: a name is unique within a trip, ignoring capitals (F3.R4).
- `UNIQUE (trip_id, position)`: the order is unique per trip. This index also serves the list query.
- The CHECK cannot test `name_key`. That rule is checked in code review.

Cascade: `people` is a child of `trips`, so deleting a trip removes its people (F2.R9, as F2's plan requires). F4 and F6 add `person_id` foreign keys to `people(id)` **without** `ON DELETE CASCADE`. The database then refuses to delete a person who is still referenced, which closes the race between the in-use check and the delete (F3.R9). F4 and F6 plans must carry this rule forward.

## Routes and API
All under `/api/trips/[id]/people`. Bodies are JSON. Errors use F1's shape `{ "error": { "code": string, "field"?: "name" } }`, with one addition: a `name_taken` error carries `existingName`, so the message can show the name as stored (F3.R4, AC5). Every route requires a logged-in session. A logged-out request gets `401` `not_logged_in`. A trip owned by someone else and a missing trip return the same `404` `not_found` body (F2.R8, F3.R11).

| Method and path | Request | Success | Errors |
|---|---|---|---|
| `GET /api/trips/[id]/people` | none | `200 { "people": [{ id, name, addedAt }] }`, oldest first, `addedAt` ISO UTC | `401` `not_logged_in`; `404` `not_found`; `500` `internal` |
| `POST /api/trips/[id]/people` | `{ name }` | `201 { "person": { id, name, addedAt } }` | `400` `blank_name` or `name_too_long` (`field` `name`); `400` `invalid_body` for unparseable JSON; `404` `not_found`; `409` `name_taken` (`field` `name`, `existingName`); `401`; `500` `internal` (no name logged) |
| `DELETE /api/trips/[id]/people/[personId]` | none | `200 { "ok": true }` | `404` `not_found` (also when already removed, F3 edge case); `409` `in_use` (F3.R9); `401`; `500` `internal` |

There is no `PATCH` or name-change route (F3.R7, AC14). Routes map service results: `not_logged_in` → 401, `not_found` → 404, `in_use` and `name_taken` → 409, validation → 400.

## Screens
- **People section** (on `/trips/[id]`, below the trip name, shown only when the trip has loaded): client component. Heading "People"; the add field is labelled "Person name" and its button reads "Add".
  - Loading: "Loading people…".
  - Failed to load: "We couldn't load the people. Try again." and a "Try again" button that fetches the list again. The list area shows only this message (F3.AC15).
  - Empty: "No people yet. Add the people on this trip." and the add field.
  - Loaded: one row per person, oldest first. Each row has a Remove button whose accessible name is "Remove [name]".
  - Add field: field errors come from `people-messages.ts` and are linked with `aria-describedby`. On a duplicate, the message uses the stored name and the typed name is kept. On any other failure, "We couldn't add this person. Try again." is shown and the typed name is kept. While in flight the button is disabled and reads "Adding…". On success the person is appended and the field is cleared.
  - Refused removal: "This person is in an expense or payment, so they can't be removed." is shown in a `role="alert"` above the list, and the person stays.
- **Remove dialog** (on the trip page, opened from a row): native `<dialog>` opened with `showModal()`, as in F2. Title, body and buttons come from `people-messages.ts`. Confirm sends `DELETE`, and the button reads "Removing…" and is disabled while in flight. Success removes the row. Failure shows "We couldn't remove this person. Try again." and the person stays. Cancel and Escape change nothing. Focus returns to the Remove button that opened the dialog.

## Tasks

### F3.T1 — Person name rules
- **Files:** `app/src/domain/person-name.ts`, `app/tests/domain/person-name.test.ts`
- **Depends on:** F1.T1 (scaffold)
- **Work:** `validatePersonName(raw: unknown)`. A non-string, or a name that is empty after `trim()`, returns `{ ok: false, code: "blank_name" }`. A trimmed name longer than 50 code points returns `{ ok: false, code: "name_too_long" }`. Length counts code points (`[...name].length`), the rule F1.T3 and F2.T1 use. A valid name returns `{ ok: true, name }` with the trimmed name; inner spaces are kept. `personNameKey(name)` returns `name.toLowerCase()`. Callers pass the trimmed name. The rule is a separate file so F2's trip-name rules are not changed.
- **Tests:** `tests/domain/person-name.test.ts`: `F3.AC1 accepts a name of 1 character`, `F3.AC2 refuses an empty name`, `F3.AC2 refuses a name of only spaces`, `F3.AC3 accepts a name of exactly 50 characters`, `F3.AC3 refuses a name of 51 characters`, `F3.AC3 counts characters by code point`, `F3.AC4 removes leading and trailing spaces`, `F3.AC4 keeps spaces inside the name`, `F3.AC5 names that differ only in capitals have the same key`, `F3.AC5 a name with trailing spaces has the same key once trimmed`.
- **Done when:** `npm test` passes the file.

### F3.T3 — Person store and usage ports, and fakes
- **Files:** `app/src/ports/person-store.ts`, `app/src/ports/person-usage.ts`, `app/tests/fakes/in-memory-person-store.ts`, `app/tests/fakes/in-memory-person-usage.ts`
- **Depends on:** F1.T4 (ports), F1.T5 (fakes convention)
- **Work:**
  - `PersonRecord = { id, tripId, name, nameKey, position: number, addedAt: Date }`.
  - `PersonStore` methods, all taking `ownerId`. The store checks that the trip belongs to the owner:
    - `listByTrip(ownerId, tripId): Promise<PersonRecord[] | null>`. `null` when the trip is missing or not owned.
    - `add(ownerId, tripId, input: { id, name, nameKey, addedAt })`. Returns `{ ok: true, person }` with `position` set to the next number on the trip, `{ ok: false, reason: "trip_not_found" }`, or `{ ok: false, reason: "name_taken", existingName }` with the stored name.

### F3.T4 — Add-person service
- **Files:** `app/src/services/add-person.ts`, `app/tests/services/add-person.test.ts`
- **Depends on:** F3.T1, F3.T3, F1.T15 (`requireUser`), F1.T5
- **Work:** `addPerson({ session, people, now, newId, logger }, { tripId, name })`. Call `requireUser({ session, now })` first. A refusal returns `not_logged_in` with no store call. Read only `input.name` and run `validatePersonName`; a failure returns its code and writes nothing. Compute `nameKey = personNameKey(name)`. Call `people.add(userId, tripId, { id: newId(), name, nameKey, addedAt: now() })`. Map `trip_not_found` to `not_found`, and `name_taken` to `{ ok: false, error: "name_taken", existingName }`. On success, log `{ tripId, personId, ownerId }` with "person added", never the name, and return `{ ok: true, person }`. The duplicate check itself lives in the store, so it is one rule that runs atomically.
- **Tests:** `tests/services/add-person.test.ts`: `F3.AC1 saves a valid name as the last person on the trip`, `F3.AC2 writes nothing for a blank name`, `F3.AC3 writes nothing for a name over 50 characters`, `F3.AC4 saves the trimmed name`, `F3.AC5 refuses "sam" and "Sam " when "Sam" is on the trip and writes nothing`, `F3.AC5 the refusal gives the stored name, not the typed one`, `F3.AC6 saves Sam on a second trip while Sam is on the first`, `F3.AC12 saves another person when the trip already has many`, `F3.AC13 refuses a request with no session and writes nothing`, `F3.AC13 a trip owned by another user gives not_found and writes nothing`.
- **Done when:** `npm test` passes the file.

### F3.T7 — Drizzle person store
- **Files:** `app/src/db/person-store.ts`
- **Depends on:** F3.T3, F3.T6
- **Work:** `createPersonStore(db)` returns a `PersonStore`. Every query uses Drizzle's parameterised builders.
  - `listByTrip` first checks that the trip belongs to the owner (`trips.id = ? AND owner_id = ?`). If not, it returns `null`. Otherwise it selects the trip's people ordered by `position`.
  - `add` runs inside `db.transaction`. It checks trip ownership and returns `trip_not_found` if that fails. It selects by `(trip_id, name_key)`, and if a person exists it returns `name_taken` with that person's stored name. Otherwise it sets `position` to the trip's maximum plus one (or 1) and inserts. If the insert fails the UNIQUE check on `(trip_id, name_key)`, because two requests raced, the store re-reads the existing person and returns `name_taken` with its name. Any other error is rethrown.
  - `findForOwner` checks ownership and that the person is on the trip.
  - `deleteForOwner` runs inside `db.transaction`. It checks ownership and that the person is on the trip, and returns `not_found` if either check fails. It deletes where `id` and `trip_id` match. If the database refuses the delete with a foreign-key violation, the store returns `in_use` (F3.R9 race guard). Other errors are rethrown.
- **Tests:** None. Checked in code review: every query filters on the owner through `trips`; no SQL is built from strings; `add` and `deleteForOwner` are each one transaction; the unique violation is mapped only for the name key; the foreign-key violation is mapped only to `in_use`; no error is swallowed (CLAUDE.md › Folder layout; project-rules.md › Testing).
- **Done when:** code review passes, and a script that adds "Sam" and then "sam" to one trip gets `name_taken` on the second call.
